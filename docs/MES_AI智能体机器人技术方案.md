## 二、AI 模型选型推荐

### 2.1 选型原则

针对本项目特点，模型选型遵循以下原则：

- **代码生成能力强**：能够高质量生成 Java、SQL、Vue.js、Shell 等多语言代码；
- **上下文窗口足够大**：能够加载完整的 MES 系统文档、数据库 Schema 及历史对话；
- **本地或私有化可部署**：确保涉密系统数据不出厂区网络；
- **推理能力稳定**：在复杂业务逻辑分析与错误排查中表现稳定；
- **成本可控**：月度费用在合同预算范围内。

### 2.2 推荐模型对比

| 维度 | Claude Sonnet 4（首选） | GPT-4o | DeepSeek-V3（本地备选） | Qwen2.5-Coder（本地轻量） |
|------|----------------------|--------|----------------------|------------------------|
| 代码生成质量 | ★★★★★ | ★★★★☆ | ★★★★☆ | ★★★★☆ |
| 上下文窗口 | 200K tokens | 128K tokens | 64K tokens | 32K tokens |
| 中文理解 | ★★★★☆ | ★★★★☆ | ★★★★★ | ★★★★★ |
| Java/Spring Boot | ★★★★★ | ★★★★☆ | ★★★★☆ | ★★★★☆ |
| SQL 优化 | ★★★★★ | ★★★★☆ | ★★★★☆ | ★★★★☆ |
| Vue.js 前端 | ★★★★★ | ★★★★☆ | ★★★★☆ | ★★★☆☆ |
| 私有化部署 | API 调用 | API 调用 | ✅ 支持本地 | ✅ 支持本地 |
| 数据安全 | 需脱敏处理 | 需脱敏处理 | ✅ 完全本地 | ✅ 完全本地 |
| 月度预估成本 | ≈ 1,500～3,000元 | ≈ 2,000～4,000元 | 服务器成本 | 服务器成本 |

### 2.3 推荐方案

**主力模型：Claude Sonnet 4（API 接入）**

理由如下：

- 在代码生成、长文档理解和系统分析方面综合能力最强；
- 200K tokens 上下文可同时加载完整数据库 Schema + 接口文档 + 业务说明；
- 通过 Anthropic API 接入，稳定可靠，无需维护 GPU 服务器；
- 调用前对敏感数据进行脱敏（厂区编号、设备序列号替换为代号），符合数据安全要求。

**本地补充模型：DeepSeek-V3（私有化部署）**

用于处理包含真实生产数据、不可脱敏的场景（如数据库直连查询优化、设备通讯协议调试），在内网环境独立运行，数据不出厂区。

**推荐双轨架构：**

```
业务需求 / 代码开发 / 报告生成
        ↓ 脱敏处理
   Claude Sonnet 4（API）

包含真实生产数据的分析任务
        ↓ 内网直连
   DeepSeek-V3（本地部署）
```

### 2.4 模型接入配置要点

- API Key 存储于内网密钥管理服务（如 HashiCorp Vault 或 IT 自建 KMS），禁止硬编码；
- 所有 API 调用经统一 AI 网关代理，记录调用日志、token 消耗与响应时间；
- 设置每日 token 预算上限（建议 300 万 tokens/天），超限自动告警；
- 本地 DeepSeek-V3 部署硬件要求：GPU 服务器（推荐 A100 80G × 1 或 RTX 4090 × 2），内存 128G+，存储 2TB NVMe SSD。

## 四、AI 训练工作流程

### 4.1 训练总体框架

AI 训练采用"理解 → 实践 → 验证 → 迭代"的闭环模式，分为三个阶段执行。

```
阶段一（第 1 月）
  系统文档输入 → AI 阅读理解 → 知识提炼 → 理解报告输出
        ↓
  测试任务下发 → AI 执行 → 结果审核 → 知识修正
        ↓
  循环训练至理解达标（理解准确率 ≥ 85%）

阶段二（第 2 月）
  真实需求输入 → AI 独立开发 → 测试报告生成
        ↓
  甲方评审验收 → 问题反馈 → AI 迭代修正
        ↓
  评审通过 → 部署演示 → 应用水平确认

阶段三（第 3～12 月）
  常态化需求处理 + 每日巡检 → 持续能力积累
```

### 4.2 第一阶段训练详细流程

#### 4.2.1 系统理解训练（第 1～2 周）

**步骤 1：数据库结构理解训练**

```
输入：数据库 DDL + 数据字典
Prompt 模板：
  "你是 MES 系统专家。请阅读以下数据库结构，
   理解每张表的业务含义、字段含义及表间关系，
   并以表格形式输出你的理解报告，
   包含：表名、业务描述、核心字段说明、关联表。"

验证方式：出题测试（给定业务场景，让 AI 写出对应 SQL）
达标标准：SQL 准确率 ≥ 85%
```

**步骤 2：接口理解训练**

```
输入：Swagger 接口文档
验证方式：给定业务需求，让 AI 列出调用链路与参数
达标标准：接口调用方案准确率 ≥ 85%
```

**步骤 3：业务流程理解训练**

```
输入：业务流程文档 + 操作手册
验证方式：场景模拟问答（如"工单从创建到完成经过哪些状态流转？"）
达标标准：业务流程描述准确率 ≥ 90%
```

#### 4.2.2 代码生成能力训练（第 3～4 周）

**训练任务设计原则：**

- 从简单到复杂，逐步升级任务难度；
- 每个任务包含明确的输入、期望输出、验收标准；
- 人工审核每次代码输出，反馈写入训练记录。

**训练任务分级：**

| 级别 | 任务类型 | 示例 | 验收标准 |
|------|--------|------|--------|
| L1 基础 | SQL 查询 | 统计当日各工序完工数量 | 结果正确，语法规范 |
| L1 基础 | 简单接口 | 查询工单列表接口 | 接口可调通，数据正确 |
| L2 中级 | 报表开发 | 月度生产效率报表 | 数据准确，格式规范 |
| L2 中级 | 业务逻辑 | 工单状态流转逻辑 | 状态机正确，边界处理完整 |
| L3 高级 | 完整功能 | 设备点检记录功能（含前端） | 前后端联调通过，测试全覆盖 |
| L3 高级 | 设备接口 | 设备数据采集接口对接 | 协议解析正确，数据入库准确 |

#### 4.3.2 Prompt 版本管理

#### 4.3.3 Prompt 漂移（Prompt Drift）监控与 MES 业务逻辑断言库

**问题背景：**

Prompt 漂移是指随着 Prompt 的累积修改，或底层 AI 模型版本升级（如从 Claude Sonnet 4 升级到后续版本），AI 对原有核心业务逻辑的理解出现静默退化——表现为相同输入产生不同输出，且退化往往在生产环境出问题后才被发现。对于封测行业 MES 系统中高度敏感的"状态机逻辑"（如工单状态流转、设备点检状态、批次追溯链路），这类退化的危害尤为严重。

**应对方案：建立 MES 业务逻辑断言库（MES Business Logic Assertion Library）**

断言库本质是一套"AI 必须答对的考题集合"，与软件测试中的回归测试用例性质相同，专门用于验证 AI 对核心 MES 业务逻辑的理解是否完整且未退化。

**断言库结构设计：**

```
/assertions
  /state-machine          # 状态机类断言
    work-order-flow.yaml  # 工单状态流转
    lot-tracking.yaml     # 批次追溯链路
    equipment-check.yaml  # 设备点检状态
  /sql-logic              # SQL 逻辑类断言
    production-stats.yaml # 生产统计查询
    yield-calc.yaml       # 良率计算逻辑
  /api-behavior           # 接口行为类断言
    interface-chain.yaml  # 接口调用链路
  /code-generation        # 代码生成类断言
    naming-convention.yaml
    error-handling.yaml
```

**单条断言的数据格式（YAML）：**

```yaml
id: SM-WO-001
name: 工单状态流转核心断言
category: state-machine
priority: critical          # critical / high / medium
description: >
  验证 AI 对工单状态机的理解：工单只能按照
  "草稿→已下达→执行中→暂停→执行中→已完成/已关闭"
  的合法路径流转，禁止跳步或逆向流转。
prompt: |
  在山东芯通 MES 系统中，一张工单当前状态为"执行中"。
  请列出：(1) 允许流转到的下一个合法状态清单；
          (2) 不允许流转的状态及原因；
          (3) 如果前端传入状态"草稿"，后端应如何处理？
expected_keywords:
  - "暂停"
  - "已完成"
  - "已关闭"
  - "非法"       # 或"不允许"、"拦截"等语义等价词
expected_excludes:
  - "草稿"       # 不应出现可以回退到草稿的表述
  - "已下达"     # 不应出现可以回退的表述
scoring_method: keyword_match  # keyword_match / llm_judge
pass_threshold: 0.90           # 90% 关键词命中率
```

**自动化基准测试流水线：**

以下三种情形会自动触发断言库全量运行：

- **模型版本变更**：检测到 AI 网关配置的模型版本号发生变化时；
- **Prompt 文件变更**：`/prompts` 目录下任意文件提交 Git 时，CI/CD 流水线自动触发；
- **定期巡检**：每周一凌晨 02:00 自动执行，输出周报。

**基准测试执行逻辑：**

```python
# 断言测试核心逻辑（伪代码）
for assertion in assertion_library.load_all():
    response = ai_gateway.call(
        prompt=assertion.prompt,
        model=current_model_version
    )
    result = scorer.evaluate(
        response=response,
        expected_keywords=assertion.expected_keywords,
        expected_excludes=assertion.expected_excludes,
        method=assertion.scoring_method
    )
    report.append(assertion.id, result)

# 汇总判定
critical_failures = [r for r in report if r.priority == 'critical' and not r.passed]
if critical_failures:
    alert.send(
        level="BLOCK",
        message=f"⛔ 基准测试失败：{len(critical_failures)} 条 Critical 断言未通过，"
                f"本次模型/Prompt 变更已被阻断，禁止上线。",
        recipients=["技术负责人", "IT 负责人"]
    )
```

**阻断规则：**

| 断言优先级 | 失败数量 | 处置动作 |
|--------|--------|--------|
| Critical | ≥ 1 条 | 立即阻断，禁止变更上线，自动回滚 Prompt 版本 |
| High | ≥ 3 条 | 告警，须技术负责人人工审核后决定是否上线 |
| Medium | ≥ 5 条 | 记录问题单，限期修复，不阻断上线 |

**断言库维护规范：**

- 每新增一个 MES 核心业务功能，必须同步新增不少于 3 条对应断言；
- 断言库文件纳入 Git 版本管理，修改须经技术负责人审批；
- 每季度对断言库进行评审，淘汰过时断言，补充新业务场景；
- 断言通过率纳入月度评估指标（目标：Critical 断言通过率 100%，全量通过率 ≥ 95%）。

### 4.4 训练质量控制

每次训练任务执行后，由技术负责人或 AI 训练工程师按以下维度评分：

| 评分维度 | 权重 | 评分说明 |
|--------|------|--------|
| 功能正确性 | 40% | 代码/SQL 执行结果是否正确 |
| 代码规范性 | 20% | 是否符合项目编码规范 |
| 完整性 | 20% | 是否包含异常处理、注释、测试 |
| 可维护性 | 20% | 代码结构清晰，逻辑易读 |

综合得分 ≥ 80 分为合格，< 60 分需重新训练并分析原因。

### 4.5 自动化回归测试体系

#### 4.5.1 回归测试的必要性

MES 系统各模块高度耦合：工单管理、物料追溯、设备状态、质量判定之间存在大量联动逻辑。AI 修复或新增功能时，可能在不知情的情况下破坏已有的业务流转——例如修改工单状态更新逻辑，可能导致关联的设备锁机规则失效。单元测试只能覆盖单个模块的孤立逻辑，无法捕获跨模块的联动回归问题。

为此，本方案引入**流量录制与回放**技术作为系统级回归测试的核心手段。

#### 4.5.2 流量录制与回放技术实现

**技术原理：**

在 MES 测试环境的 API 网关层部署流量录制探针，持续录制过去 24 小时的真实业务操作请求（请求方法、路径、参数、响应体、响应码），脱敏处理后存入回放库。当 AI 提交新代码并部署至测试环境后，自动将录制流量在新版本上重放，比对新旧响应差异。

**架构示意：**

```
正常业务流量
      ↓
  MES 测试环境 API 网关
      ├── 正常处理请求（返回给用户）
      └── 流量镜像 → 脱敏处理 → 流量录制库（保留 24 小时）

AI 提交新代码后：
  流量录制库 → 回放引擎 → 新版本 MES 测试环境
                   ↓
           响应差异比对引擎
                   ↓
         回归测试报告（差异项 + 风险评级）
```

**推荐工具：**

- **GoReplay（gor）**：轻量级 HTTP 流量录制与回放工具，支持按比例镜像流量，无需修改 MES 应用代码；
- **Diffy（Twitter 开源）**：多版本响应差异比对框架，可自动过滤时间戳、动态字段等无意义差异；
- **自研脱敏过滤层**：在录制入库前，自动替换请求/响应中的敏感字段（见第九章脱敏层规范）。

**回放执行流程：**

```
① AI 提交代码 → GitLab CI 触发构建
② 新版本自动部署至【回归测试专用环境】（与日常测试环境隔离）
③ GoReplay 从录制库取出过去 24 小时流量（约 500～2000 条请求）
④ 流量回放至新版本环境，同步回放至旧版本环境（基准对照）
⑤ Diffy 比对新旧版本响应差异：
     - 响应码变化（200→500 为严重问题）
     - 响应体核心字段差异（工单状态、数量、物料编码等关键字段）
     - 响应时间劣化（新版本 P99 超出旧版本 150% 触发告警）
⑥ 生成差异报告，按差异严重程度分级
⑦ 差异项超过阻断阈值 → 拒绝本次代码合并，通知 AI 重新修复
```

#### 4.5.3 回归测试差异分级与阻断规则

| 差异类型 | 判定标准 | 级别 | 处置 |
|--------|--------|------|------|
| 响应码由 2xx 变为 4xx/5xx | 任意接口出现 | P0 严重 | 立即阻断，禁止合并，AI 必须修复 |
| 工单状态字段值变化 | 非预期变更 | P0 严重 | 立即阻断 |
| 批次/物料关键字段值变化 | 非预期变更 | P0 严重 | 立即阻断 |
| 响应结构新增/删除字段 | 未在需求单说明的变化 | P1 高危 | 人工审核后决定 |
| 响应时间劣化 > 150% | P99 响应时间对比 | P1 高危 | 人工审核后决定 |
| 非关键字段格式变化 | 如时间格式、数字精度 | P2 中危 | 记录，限期整改 |
| 纯新增接口无旧版本对照 | 新功能 | 忽略 | 走正常验收流程 |

**阻断规则：** 存在任意 P0 级差异，或 P1 级差异 ≥ 3 条时，CI/CD 流水线自动阻断代码合并，并在任务管理平台展示详细差异报告，AI 需针对每个差异项给出说明或修复方案，经技术负责人确认后方可重新提交。

#### 4.5.4 回归测试与业务断言库的协同

流量回放测试与断言库测试形成双重防护：

```
AI 提交代码
      ↓
① 业务逻辑断言库（4.3.3）
   验证 AI 的"理解层"：核心业务逻辑理解是否正确
      ↓（全通过）
② 流量回放回归测试（4.5）
   验证 AI 的"执行层"：实际代码运行结果是否影响存量业务
      ↓（全通过）
③ 人工代码 Review（技术负责人抽检）
      ↓（通过）
④ 提交甲方验收测试
```

## 七、编写过程实时进展查询与人工授权机制

### 7.1 实时进展查询

#### 7.1.1 进展推送机制

AI 执行任务过程中，通过以下机制实时更新进展：

- **WebSocket 推送**：前端与后端保持长连接，AI 每完成一个执行步骤即推送进展消息，无需手动刷新；
- **进展阶段划分**：AI 任务执行分为 5 个可观测阶段：

```
① 需求理解中（0～15%）
   AI 正在解析需求，检索相关知识库，生成实现方案

② 方案确认中（15～20%）⚠️ 需人工确认
   AI 输出实现方案摘要，等待授权人确认后继续

③ 代码生成中（20～80%）
   AI 逐步生成代码，日志实时显示生成进度

④ 自动测试中（80～95%）
   AI 执行单元测试 + 接口测试，生成测试报告

⑤ 报告生成中（95～100%）
   AI 生成完整交付物：代码文件清单 + 测试报告 + 使用说明
```

- **执行日志实时流**：任务详情页提供实时日志流视图（类终端界面），显示 AI 每次模型调用的输入摘要与输出结果，供技术人员监控；
- **消息通知**：关键状态变更（评审通过、AI 完成、待验收等）通过企业微信/钉钉或邮件推送通知相关人员。

### 7.2 人工授权机制

#### 7.2.1 授权触发节点

以下节点 AI 必须暂停执行，等待人工明确授权后方可继续：

| 正式环境部署 | 测试通过，申请上线时 | IT负责人 | 不得超时，必须明确审批 |
| 紧急修复执行 | 生产故障需紧急修复时 | IT负责人（电话/即时授权） | 最高优先级，30分钟内响应 |

### 9.2 脱敏层（PII Filter）技术规范

#### 9.2.1 脱敏规则清单

| 数据类型 | 识别方式 | 脱敏规则 | 示例 |
|--------|--------|--------|------|
| 设备序列号 | 正则：`[A-Z]{2}\d{8,12}` | 保留前2位+后2位，中间替换 | `AB****3456` → `[DEVICE_SN_AB3456]` |
| 员工工号 | 正则：`EMP\d{6}` 或 NLP识别 | 全量替换 | `EMP001234` → `[EMP_ID_***]` |
| 生产批次号 | 正则：`LOT[A-Z0-9]{10,16}` | 全量替换 | `LOTAB202601001` → `[LOT_NO_***]` |
| 内网 IP | 正则：`192\.168\.\d+\.\d+` | 全量替换 | `192.168.1.100` → `[IP_ADDR_***]` |
| 厂区编号 | 白名单比对（预配置） | 全量替换 | `FAB-NJ-01` → `[SITE_PARAM_***]` |
| 数据库连接串 | 正则：`jdbc:mysql://.*` | 全量替换 | → `[DB_CONN_***]` |
| 身份证号 | 正则：18位身份证 | 全量替换 | → `[ID_CARD_***]` |

#### 9.2.2 硬编码扫描器规范

AI 生成的代码在提交 Git 之前，CI/CD 流水线自动执行硬编码扫描，检测并拒绝以下情况：

- 代码中出现任何在脱敏规则白名单中的厂区特定字符串；
- 出现 IP 地址直接硬编码（服务地址必须通过配置文件或环境变量注入）；
- 出现明文密码、API Key、数据库密码等敏感凭据；
- 出现生产环境数据库名、表名的直接硬编码（必须通过配置文件管理）。

扫描工具：自研 Python 脚本 + Gitleaks（开源敏感信息扫描工具），集成于 GitLab CI Pipeline 的第一个 Stage，扫描失败则整个流水线终止。
