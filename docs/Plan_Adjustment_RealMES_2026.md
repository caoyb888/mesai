## 一、背景与触发变更

此前因甲方业务材料未到位，项目采用 **ITSM 验证版** 策略（用 ITSM 系统跑通工具链，训练评分 ~91%）。
**2026-07 已取得真实 MES 库的访问地址、账号、密码及数据字典**，形势发生实质变化：

| 维度 | 原假设 | 真实情况（本次确认） |
|------|--------|--------------------|
| DBMS | 测试环境判定 PostgreSQL | **Oracle**（业务逻辑大量在 PL/SQL 存储过程/包/函数中） |
| 环境性质 | — | **克隆测试副本**（只读仍按 CLAUDE.md 执行；副本可能仍含真实数据，脱敏不可省） |
| 数据源 | 手工整理 SQL 文件（ITSM） | 需转为**自动化数据库自省**（手工不可行） |
| 数据质量 | 假设注释规范 | 注释不规范/**乱码**（Oracle 中文库常见 ZHS16GBK 编码问题） |

## 二、规模实测（据 `docs/data_dictionary_full.csv` 字段级字典）

| 指标 | 数值 | 说明 |
|------|------|------|
| Schema 数 | 2 | `MESAPUSER`（业务）、`SCOAPUSER`（框架/系统） |
| 表数 | **2,121** | 去重 SCHEMA.TABLE |
| 字段数 | **81,360** | 字段级明细 |
| 有注释字段 | 60,962 | 其中中文注释 30,049、**非中文/疑似乱码 18,248** |
| 空注释字段 | 20,398 | 需靠命名+数据+存储过程用法推断语义 |
| 系统字典表 | `SCO_DATA_DIC` ≈ 20,266 条 | 最大的一手语义来源（SCOA0020 界面） |
| **存储过程/包/函数** | **字典 CSV 未覆盖** | ⚠️ 本次自省的**最大增量**，是业务逻辑主要载体 |

**结论**：规模是 ITSM 验证版的数十倍；字段字典虽有，但**存储过程完全缺席**且**注释质量参差**。
方案核心 = 自动自省 + 存储过程理解 + 编码治理 + 规模分级。

## 二·补 实测发现（`encoding_normalizer.py` 对全量字典 CSV 治理，2026-07-06）

对 `data_dictionary_full.csv`（81,360 字段）治理，1.2 秒完成，分级：
clean 56,510 / empty 20,398 / **garbled 4,452**（其中 4,449 为 `????` 问号化）/ recoverable 0。

两点关键结论：

1. **本 MES 是韩系系统，注释含中/韩/英三语**（如 `인장시험`=拉伸试验、`시편번호`=试样编号）。
   → **理解训练（S3）必须处理韩文**：AI 需具备韩文注释理解或建立中韩术语对照表；否则大量字段语义丢失。
2. **CSV 里可恢复乱码为 0**：字典导出时字符集转换已把原始乱码降级为 `????`（不可逆）。
   → **可修复的 Latin-1 乱码只会在 `db_introspect.py` 直连 Oracle（拿原始字节）时出现**；
   编码治理的修复价值在"直连自省"阶段兑现，对已导出的 CSV 只能识别"空 + 已损毁"。
   → S2.9-3 顺序上应**紧跟 S2.9-2 直连自省**，不要只依赖现成 CSV。

## 二·补二 真实库首次自省（2026-07-06，详见《MES 资产盘点报告》AI-MES-CENSUS-2026-001）

已实际连上真实库（Oracle 21c XE / XEPDB1 / **AL32UTF8**）跑通自省，实测颠覆若干假设：

1. **PL/SQL 达 193 万行、9160 个单元，业务逻辑压倒性在「包」**（MESAPUSER 4563 包 + 4421 包体）。
   → 全量训练不可行，P0 分级是硬约束；包体粒度粗（单个最大 1.6 万行），P0 包需子程序级细化。
2. **克隆库列注释全空（0 条）** → 字典 CSV 是**唯一列语义来源**，`dict_reconcile` 的"字典反哺"从补充变主场景；
   但 **PL/SQL 源码内含可读中文行注释**，是恢复语义的重要补充。
3. **字符集 AL32UTF8**，活库无 GBK 乱码 → 编码治理重心转向字典 CSV 本身。
4. **大量动态 SQL（EXECUTE IMMEDIATE）** → 静态分析盲区，`proc_parser` 已标记，需人工/运行期补表依赖。
5. **`ALL_*` 视图在 DBA 账号下慢**、MESAPUSER 源码巨大 → `db_introspect` 已加 `--no-source`；后续可加 `DBA_*` 快速路径。

## 三、核心策略调整（4 条）

1. **手工喂料 → 自动自省**：新增 `db_introspect.py`（只读、Oracle 适配层），抽取表/字段/约束/索引/注释 +
   **存储过程/函数/包/触发器源码与签名**，产出结构化 JSON。
2. **存储过程升为一等训练对象**：新增"提取 → 依赖图谱 → 理解训练 → 行为断言"链路；业务流程理解改为**以存储过程为锚点**。
3. **前置编码治理层**：`chardet` 探测→转码 UTF-8→注释质量三级分级（clean/可恢复/乱码）；乱码项**不静默修改**，
   产出《注释乱码清单》交甲方/人工确认；语义无法从注释获取时，改由 AI 从"命名+数据样本+存储过程用法"推断。
4. **规模驱动分级**：先盘点真实数量，再按 P0 核心（工单/批次/设备/质量相关表与入口存储过程）/P1/P2 分批，
   适配 Token 预算（300 万/日）与低配机器。

## 四、工具链改造（扩展 `scripts/kb-ingest/`）

| 组件 | 职责 | 状态 |
|------|------|------|
| `db_introspect.py` | 只读 Oracle 自省 → 结构化 JSON（含存储过程源码/签名）；DBMS 适配层 + 假数据自测 | 🆕 本次交付骨架 |
| `encoding_normalizer.py` | 编码探测/转码/注释质量三级分类 + 乱码清单 | 🆕 待建 |
| `proc_parser.py` | 解析 PL/SQL：引用表(读)、写副作用、调用链、状态流转、硬编码/PII 候选、动态 SQL 标记 | ✅ 完成+自测 |
| `dependency_graph.py` | 消费 proc_parser 边 CSV，构 过程→表、过程→过程 图；入口过程/高被引表/环检测→P0/P1/P2 分级 | ✅ 完成+自测 |
| `dict_reconcile.py` | 自省 JSON vs `data_dictionary_full.csv` 对账（类型/注释/缺失），含「字典反哺库空注释」清单 | ✅ 完成+自测 |
| `ddl_parser.py` / `kb_ingest.py` | 适配自省 JSON；新增"存储过程卡片" chunk 类型 | 🔧 改造 |
| 前置轻量脱敏 | 自省结果→送 AI 之间强制过滤（扩展 `src/ai-gateway` desensitize 覆盖 PL/SQL 源码） | 🔧 前移 |

> **Sprint 2.9 工具链已全部就绪（5/5，纯 stdlib，kb-ingest 全套 129 单测通过）**，五工具共享同一自省 JSON 契约、端到端管道已贯通：
> ```
> Oracle ─→ db_introspect.py ─→ metadata.json
>    ├─ encoding_normalizer.py ─→ 注释乱码清单（+字典CSV亦可直接治理）
>    ├─ proc_parser.py ─→ 依赖边.csv + 硬编码PII.csv
>    │      └─ dependency_graph.py ─→ P0 核心资产报告（表/过程分级）
>    └─ dict_reconcile.py（× data_dictionary_full.csv）─→ 对账差异清单 + 字典反哺清单
> ```
> 待测试机就绪即可直连真实库跑通。低配机上已用真实字典 CSV 与假数据完成全部验证。

## 六、机器 / 性能策略

| 环节 | 资源 | 低配可跑 | 建议 |
|------|------|---------|------|
| 数据库自省 | I/O 为主 | ✅ | 靠近 DB 跑；`oracledb` thin 模式免装客户端 |
| 编码治理 / PL/SQL 解析 | CPU 轻中 | ✅ | 批处理、可断点续跑 |
| **向量化/Embedding** | 内存/算力重 | ⚠️ | 用 **Kimi API Embedding**（已具备），避免本地大模型；分批+增量 |
| AI 理解训练 | 网络+Token | ✅ | P0 分级控预算；250 万降级 / 300 万暂停 |

**测试机建议画像**：≥8C/32G/≥100G 磁盘；可达 Oracle 库（1521）；可出网调 AI 网关；GPU 非必需。

## 七、主要新增风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 存储过程源码含硬编码/敏感值随源码外发 | 极高 | 脱敏前移至 Sprint 2.9；DBA 审核规则覆盖 PL/SQL |
| 规模超预期致 Token/工时爆表 | 高 | 先盘点→P0/P1/P2 分级→分批，不求一次全量 |
| 注释乱码致语义误解 | 中高 | 三级分级 + 代码/数据推断 + 乱码清单人工确认 |
| 误连生产 / 写操作 | 极高 | 只读账号；确认副本；CLAUDE.md 红线 |
