## 一、背景与问题定义

mes-sql 取数链路已三层贯通并接入真实 MES 只读库（REQ-MES-AI-20260730-001）。上线首日的真实使用中，
生成准确率暴露了系统性短板——四类典型失败全部实测发生：

| # | 实测失败 | 根因分类 | 当日处置 |
|---|---------|---------|---------|
| 1 | `SPEC_CD` 臆造列（ORA-00904） | 字段级臆造 | Prompt 铁律 8（逐字一致）|
| 2 | `TRUNC(FCE_CH_DTM)`（ORA-00932） | 类型误用（VARCHAR2(14) 当 DATE） | Prompt 铁律 6（字符串比较）|
| 3 | `PROD_JDG_DTM` 近义臆造（ORA-00904） | 字段级臆造 | 铁律 8 + schema 校验环 |
| 4 | 代码字段用中文标签过滤（结果恒空） | 码值缺失 | 代码字典定向注入（铁律 9）|

**核心判断**：当前架构是「单趟 RAG + Prompt 约束」，本质是让模型一次猜对，猜错就把错误抛给用户。
继续堆 Prompt 规则收益递减（v1.0→v1.2 三轮迭代已验证）。需要架构级改进，而非补丁级改进。

**方法论原则**：先建立可度量的评测基线，再按 ROI 排序逐层改进，每层改动用基线数字验证效果。

## 二、提升方案总览（四层，按 ROI 排序）

```
第 1 层  评测基线（前提）────────── 可自动评分的 Text-to-SQL 基准，准确率数字化
第 2 层  执行反馈自纠错（核心）──── 生成→校验/试执行→失败回喂→重生成，最多 2~3 轮
第 3 层  语义层 + 黄金样例库 ────── 高频业务问题模板化；验证通过的查询沉淀为 few-shot 样例
第 4 层  微调（可选，最后考虑）──── 执行验证过的（问题,SQL）对微调开源模型，教方言不教 schema
```

## 三、第 1 层：评测基线

### 3.1 目标

把"感觉错误率高"变成可比数字，作为所有后续改动的验收标尺。

### 3.2 方案

- **题库**：`docs/L1L4_业务问答验收集_v0.1`（75 题）+ S3-1 SQL 验证题（30 题）中适合取数的题目，
  每题人工标注标准 SQL（ golden SQL ）。
- **评分口径**：**执行结果等价**——生成的 SQL 与 golden SQL 分别在只读库执行，
  结果集一致（行列内容比对，允许行序差异）即判对；执行失败/未生成记 0 分。
  辅以中间指标：生成率、schema 校验通过率、首轮执行成功率。
- **工具**：`scripts/verify/` 下新增评测脚本（调用 `/mes-sql/query` 批量跑题 + 自动评分 + 出报告）。
- **基线动作**：当前系统先跑一遍，记录 v1.2 + 双保险状态下的基线准确率。

### 3.3 产出

- 评测脚本 + 标注题库（jsonl）+ 基线报告（`docs/`）。

## 四、第 2 层：执行反馈自纠错循环（核心工程）

### 4.1 架构

```
用户问题
  → Schema Linking（确定性候选表/列抽取：字典直查 + 向量检索双路）
  → LLM 生成（Prompt 注入：最小列子集含真实类型 + 码值 + few-shot 样例）
  → schema 校验 + 只读试执行
      ├─ 通过 → 返回结果
      └─ 失败 → 错误信息 + 相关表真实列清单 回喂 LLM → 重新生成（≤3 轮）
                  └─ 仍失败 → generated=false + 可读原因返回
```

### 4.2 关键设计点

| 设计 | 说明 | 依据 |
|------|------|------|
| **错误回喂重试** | 把 ORA 错误/schema 校验失败原因 + 该表 all_tab_columns 真实列清单回传网关重新生成 | 当日四类失败，模型拿到真实列清单后第二轮大概率改对；BIRD/Spider 基准上执行反馈普遍提升 10~20 点 |
| **Schema Linking 前置** | 生成前从问题确定性抽取候选表/列，Prompt 只放相关表的最小列子集（含 VARCHAR2(14) 等真实类型），替代整表卡片 | 上下文越准臆造越少；类型 2 失败（TRUNC 误用）的直接预防 |
| **失败才重试** | 首轮成功的请求不加价；仅失败请求进入重试循环 | §12 预算管控：正常路径 token 不放大 |
| **候选采样择优（可选）** | 重试仍失败时，采样 3 个候选各试执行，选"可执行+行数合理"者 | self-consistency，低成本再提一档 |
| **采样值注入（可选）** | 对代码字段 `SELECT DISTINCT` 真实值（限量）注入上下文 | 有了只读连接即可做；可识别"库中无此类数据"（如今日全表合格记录）|

### 4.3 与既有资产的关系

当日落地的「双保险」不白做，恰好是循环的地基：
- `SqlSchemaValidator`（执行前校验）→ 循环的**失败检测器**；
- `code_dict` 码值注入 → 生成侧的**弹药供给**，保留；
- Prompt 铁律 6/8/9 → 保留，作为首轮生成的约束。

### 4.4 改动范围（预估）

- 网关 `mes_sql.py`：支持带"上轮错误 + 真实列清单"的重试请求（messages 追加 assistant/user 轮次）；
- Java `MesSqlService`：失败时组装真实列清单 → 回调网关重试（≤3 轮）→ 终止条件与可读失败返回；
- schema linking：网关侧新增候选列抽取（复用 `data_dictionary_full.csv` + 向量检索）；
- 测试：重试收敛/重试耗尽/预算熔断用例；评测基线前后各跑一遍对比。

## 五、第 3 层：语义层 + 黄金样例库

### 5.1 语义层（高频问题模板化）

- 现状：用户问题 80% 是高频业务统计（判定分布、炉次统计、实绩查询）。
- 方案：`指标口径表_v0.1`（17 指标）机器化——每指标固化「业务词 → 表/列/连接/过滤/码值映射」，
  命中指标走模板化 SQL（参数化时间窗等），自由生成仅兜底长尾。
- 收益：命中率内准确率接近 100%，且口径可审计、可评审。

### 5.2 黄金样例库（few-shot，越用越准）

- 种子：75 题验收集的标准 SQL。
- 增长：用户确认"结果正确"的查询自动入库（前端加"结果有用"反馈按钮）。
- 使用：生成时按相似度检索 2~3 个样例注入 Prompt。
- 零训练成本，随使用持续提升。

## 六、第 4 层：微调（可选，最后考虑）

- **能做**：用只读连接自动批量生成（问题, SQL）对（表卡片+字典组合出题，执行验证筛正确），
  微调 Qwen2.5-Coder 级开源模型。
- **教什么**：Oracle 方言习惯、VARCHAR2(14) 时间处理、禁 SELECT * 等风格——可固化进权重。
- **教不了什么**：schema 知识。1,860 表 / 78,526 字段不可能进权重，检索层永远必需。
- **代价**：数据准备/训练/评测/部署维护成本高，模型升级即重来。
- **结论**：仅当第 2、3 层完成后长尾准确率仍不达标时立项评估。

## 七、实施路径与里程碑

| 阶段 | 内容 | 预估 | 验收 |
|------|------|------|------|
| M1 | 评测基线：题库标注 + 评分脚本 + 当前系统基线报告 | ~1 周 | 基线准确率数字落档 |
| M2 | 执行反馈自纠错（含 schema linking） | 2~3 天 | 基线复测，首轮成功率+端到端准确率显著提升（目标 +15 点以上）|
| M3 | 黄金样例库 + 用户反馈闭环 | 2~3 天 | 样例检索注入生效，复测再提升 |
| M4 | 语义层（17 指标机器化） | 另行立项 | 指标命中问题准确率 ≥95% |
| M5 | 微调评估 | 视 M2/M3 结果 | 立项评审决定 |

## 八、风险

| 风险 | 缓解 |
|------|------|
| 重试循环放大 token 消耗 | 仅失败请求重试；轮次硬上限 3；预算闸熔断（§12）|
| 重试引入新臆造 | 每轮都过 schema 校验 + 安全校验，防线不降级 |
| golden SQL 标注质量 | TL/BIZ 评审标注，抽样复核（承 Phase-1 人工评分机制）|
| 语义层口径业务争议 | 指标口径须业务方签字确认后机器化 |
