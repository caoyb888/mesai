## 一、修订缘由

v1 四层方案（评测基线 → 执行反馈自纠错 → 语义层/黄金样例 → 微调）方向正确，第 1、2 层已落地。
但 M1 基线复测数字与失败归因暴露出 v1 排序与核心机制存在两处系统性错配，需在落地下一阶段前修订：

1. **押注点与主力失败错配**：v1 核心押在「执行反馈自纠错」——把 ORA 报错 / schema 校验失败回喂重生成。
   但基线失败分布中 `wrong_result`（SQL 可执行、返回数据、但数据错）占 **25/41（61%）**，
   这类失败**既不报 ORA 错、也不被 schema 校验拦截**，错误回喂循环对其**完全不可见**。
   继续以错误回喂为核心，天花板约在 `exec_fail`(4) + `blocked`(2) ≈ +15% 上下，难以达到 68.3% 目标。
2. **语义层被过度后置**：v1 将语义层/黄金样例列为第 3 层、微调列为第 4 层「另行立项」。
   但在 2.4% 的现实起点下，高频问题模板化是**最快拿到可用准确率的杠杆**，应前移与自纠错同期。

**核心判断（修订）**：真正的瓶颈是**语义接地失败**（选错表/列/码值），不是 SQL 语法。
故 v2 的主线由「一次生成 + 错误回喂」改为「**强接地检索 + 执行外的多信号校验 + 高频模板化**」三线并进，微调仍垫底。

## 二、诊断依据（基线一手数据）

| 维度 | 数字 | 出处 |
|------|------|------|
| 首轮结果正确率 | **2.4%（1/41）** | M1 报告 §3.1 确认轮 |
| 生成率 / 首轮执行成功率 | 78.0% / 63.4% | 同上 |
| 判定分布 | wrong_result **25** / not_generated 9 / exec_fail 4 / blocked_schema 2 / correct 1 | M1 报告 §3.1 |
| 分层准确率 | 单表 **0/9**、时间窗 **0/15**、码值过滤 1/11、聚合 **0/6** | M1 报告 §3.1 |
| 失败主因 | 表选错 ~10、时间谓词错乱 ~5、列选错/形状错 ~5、码值用中文标签 ~2、RAG 未召回 9 | M1 报告 §四 |
| 题库盲区 | 多表 JOIN **0 题**（JOIN 准确率完全未测） | M1 报告 §二 |

**读数**：能生成、能执行，但**答案错**。单表题都 0/9，说明失败发生在「选对表/列/值」这一步，早于 SQL 语法。

### 2.1 现 schema_linker 的结构性缺陷

`src/ai-gateway/app/services/schema_linker.py` 的候选表选择 `_candidate_tables()` 是**纯词法匹配**：
依赖 ① RAG 卡片里的 `[表]` 标记；② 问题中逐字等于表名的大写 token；③ 文档全文 token 兜底。

- **缺陷**：中文业务问题几乎不含 `SMS_HEAT` 这类英文表名，路径 ② 基本失效，选表实际全靠那个
  **152K 的 chromadb 表级向量库**召回——而它正在失败（表选错 + 未召回合计约 19/41）。
- **粒度**：只有表级卡片，无列级、无值级嵌入，信息密度不足以区分「计划表 vs 实绩表」「切割表 vs 板坯表」。
- **无值域**：字典只有列名+类型，**没有码值内容**，无从判断 `'进行中'` 是标签而非码值。

## 四、主线 P1：强接地检索与选表（修 2.4% 病根）

### 4.1 两段式语义检索

- **第一段·选表**：用**富表卡片**嵌入（表名 + 中文注释 + 全部列名 + 业务同义词 + 3~5 条样例 NL 问题），
  替代当前信息稀薄的表级卡片。检索返回 Top-K 候选表（K≈6~8）。
- **第二段·选列**：在候选表内做**列级检索**（列名 + 类型 + 注释 + 业务词嵌入），
  产出最小列子集注入上下文。保留现 `schema_linker` 的列裁剪与真实类型注入逻辑（那部分是对的）。

### 4.2 业务词 → 表/列 同义词典（离线建，可人工审）

固化高频业务词到 schema 对象的映射，作为检索的**确定性召回增强**（与向量检索并联）：

| 业务词 | 映射方向 |
|--------|---------|
| 炉次 | *HEAT* 系列 |
| 板坯 | *SLAB* 系列 |
| 实绩 / 实际 | *RSLT* / 实绩类表（**非**计划表） |
| 计划 / 排程 | *SCH* / *PLAN* 类表（**非**实绩表） |
| 判定 / 合格 | 质量判定类表 + 对应码值列 |

直接打掉「计划表↔实绩表」这类高频语义混淆（基线 Q01/Q10/Q13）。

### 4.3 相似表消歧步骤

当计划表与实绩表（或切割表与板坯表）同时进入候选，在上下文里**显式对比标注**
（「此表=计划、彼表=实绩，取数问题选实绩」），强制模型二选一，而非默默选错。

### 4.4 嵌入模型微调（性价比最高的一步）

用「问题 → 正确表」配对做对比学习，微调一个**小嵌入模型**替换通用嵌入。
修召回的 ROI 远高于微调生成大模型（见 S5）。配对数据来自 S4 的自动造对 + 黄金样例。

## 五、主线 P2：执行外多信号校验（补 61% wrong_result 盲区）

**设计原则**：`wrong_result` 不报错，所以必须引入「执行报错」之外的校验信号，让自纠错**看得见**这类失败。

| 信号 | 机制 | 打击的失败类 |
|------|------|-------------|
| **值域接地（最关键）** | 离线建「码值 + 中文标签↔码值」索引；生成后校验每个字面量过滤值是否真实存在于该列，`'进行中'` 判非法并重映射为码值；「应有数据却返回空集」报警回喂 | 码值用中文标签、恒空结果 |
| **臆造过滤拦截**（§9.1 冒烟新增） | 校验每个 `WHERE` 过滤列/值是否问题真需要：问题未提及的状态/归档类列（如 `ARCHIVE_FL`、`HEAT_STS`）不得凭空加；换更强模型后此类"无报错却结果偏少/空集"成为主要残留错 | 臆造额外过滤条件（强模型新暴露） |
| **结果级自一致** | 采样 N 候选全部执行，对**结果集**投票（非对 SQL 文本投票），优先「可执行 + 非空 + 形状合理」者 | 表/列/谓词随机性错误 |
| **LLM 复核官（critic）** | 第二遍：给 schema + 样例值 + 问题，问「此 SQL 结果能否回答问题？应用哪表/哪列/什么过滤」 | 选错表/选错列（无报错） |
| **形状校验** | 明细 vs 汇总（COUNT↔明细）、聚合粒度与问题一致性检查 | 形状错（基线 Q12） |
| **歧义反问** | 计划 vs 实绩、明细 vs 汇总不确定时，智能体澄清而非硬猜 | 语义歧义 |
| **相对/绝对时间窗区分** | 修订铁律 6：相对窗（近 N 天）用 `SYSDATE-n`，绝对窗（2024 年 8 月）用字面区间；Prompt 显式分流 | 时间谓词错乱（基线 15 题时间窗 0/15） |

> 与既有资产关系：现 `SqlSafetyValidator` / `SqlSchemaValidator` 保留为**首轮与每轮重试的硬防线**；
> P2 的新信号是在其之上补「语义正确性」维度，防线只增不减。

## 六、主线 P3：语义层 + 黄金样例库（前移，与 P2 同期）

### 6.1 语义层（高频问题模板化）

- 依据：用户问题约 80% 为高频业务统计（判定分布、炉次统计、实绩查询）。
- 方案：`指标口径表`（17 指标）机器化——每指标固化「业务词 → 表/列/连接/过滤/码值映射」，
  命中指标走**参数化模板 SQL**（时间窗等参数化），自由生成仅兜底长尾。
- 收益：命中题准确率 ≥95% 且口径可审计；模板同时是长尾生成的**黄金 few-shot 种子**。

### 6.2 黄金样例库（反馈闭环，越用越准）

- 种子：评测题库标准 SQL + 语义层模板。
- 增长：前端「结果有用」按钮，用户确认正确的查询自动入库。
- 使用：生成时按问题相似度检索 2~3 例注入 Prompt。零训练成本、随使用提升。

> **排序修订理由**：2.4% 起点下，模板化是最快拿到可用准确率的杠杆，故由 v1 的「第 3 层/另行立项」
> 前移至与 P2 同期推进。

## 七、支撑 S4：离线资产建设（"训练"的主体）

**关键认知**：1860 表 / 78,526 列的体量下，**主要工作不是训练权重，而是用「只读数据库连接 + 数据字典」离线构建资产**。
schema 知识永远在检索层，不进权重。

1. **值索引**：只读连接批量 `SELECT DISTINCT` 各码值/枚举列，建「码值 ↔ 中文标签」映射（P2 值域接地依赖）。
2. **富表/列卡片**：LLM 从注释 + 样例行自动生成业务同义词与样例 NL 问题，高频对象人工审核（P1 检索依赖）。
3. **自动造 (问题, SQL) 对**：字典 + 表组合出题 → 只读执行验证 → 留正确者 → 既做黄金样例库、也做微调与嵌入微调语料。
4. **评测扩容补 JOIN**：现题库 41 题、**0 道多表 JOIN**，等于 JOIN 准确率未测。扩至 150+ 题、覆盖多表 JOIN，
   否则 P1~P3 的 JOIN 效果测不出来。

## 八、支撑 S5：微调（垫底，只教方言）

- **能教**：Oracle 方言习惯、`VARCHAR2(14)` 时间处理、禁用中文标签/禁 `SELECT *` 等风格——可固化进权重。
- **不能教**：schema 知识（7.8 万列进不了权重），检索层永远必需。
- **优先级**：**嵌入模型微调（P1.4）优先于生成大模型微调**——修检索召回的 ROI 更高。
  生成大模型微调仅在 P1~P3 完成、长尾仍不达标时立项。
- **语料**：全部来自 S4.3 执行验证过的配对，杜绝未验证数据污染。

## 九、模型与评测两个前置动作

- **模型 A/B（P0，完整 41 题已跑，见 §9.1/§9.2 与 `docs/Text2SQL_模型对比AB报告_2026-09-07.md`）**：
  现网关实际跑的是 **`moonshot-v1-32k`**——月之暗面第一代开发档小模型（`config.py:29` 注释即"开发用小模型；
  生产用 claude"），**不是 Kimi 2.6 / K3**；Kimi 账户已具备 k2.6/k3/k2.7-code 却未启用。**结论：切 `kimi-k3`
  是近零成本最大单点收益**（受控严格正确率 2.4%→~29%、选表→97%；k3 优于 k2.6）。
- **评测先扩容**：41 题、0 JOIN、1 题 = 2.4 个百分点，分辨率过粗。先扩至 150+ 题、分层含 JOIN，
  再开始 P1~P3，才测得动效果（承 REQ-002 F1 分层口径）。

### 9.1 模型对比冒烟结论（2026-09-07，8 题受控）

**方法**：取 M1 四类实测失败 + 单表/时间窗/码值 0 分层共 8 题，给两模型**完全相同**的候选表列上下文
（schema_linker 风格，隔离检索变量）+ 相同 system prompt，只换模型；上下文经脱敏门后外发；
生成 SQL 与 golden 背靠背在只读库执行、结果集等价判分。Kimi 臂取 M1 文档已记录结论（零额外 token）。

| 维度 | smart-text（DeepSeek-V4 级） | moonshot-v1-32k（基线） |
|------|------|------|
| 选对表 | **8/8** | M1 头号失败（表选错 ~10 题） |
| 码值用码值非中文标签 | **2/2**（Q07/Q14 用 'P'） | Q14 用 `'进行中'`→恒空（失败） |
| 字符串时间列处理 | Q07 `substr` 正确 | 铁律 6 副作用误用 `TO_CHAR(SYSDATE)` |
| 结果集完全等价 | 2/8（含逻辑对仅差 `round()` 则 3/8） | M1 基线 1/41 |

**判断**：换更强模型**直接消掉基线头号失败类**（选错表、用错码值），是必要的一大步；
但**不足以单独达标**，且暴露出一个新失败模式——**臆造额外过滤条件**：

- Q05/Q12 自加 `ARCHIVE_FL='Y'/'F'`、Q01 自加 `HEAT_STS='P'`——问题未要求，导致结果偏少/空集；
- Q12/Q14/Q20 为**形状/列选择**分歧（明细 vs 汇总、`规格`理解成 `MTL_NO` 而非尺寸列、单值 vs 分布）。

**对方案的校准（P0 证据）**：

1. **模型 A/B 值得做**：移除主力失败类。建议按"并行网关"完整 41×3 量化确认（进行中，另出报告）。
2. **P2 值域接地更该做**："臆造 `ARCHIVE_FL`/`HEAT_STS` 过滤"正是 P2 靶子——校验每个过滤列/值是否问题
   真需要、是否存在于该列，直接拦这类**无报错**的错。**本发现将"臆造过滤"补入 P2 校验信号清单（见 §五）。**
3. **P3 语义层/黄金样例更该做**：形状与列选择分歧（`规格`=尺寸列、明细 vs 汇总）靠口径固化 + few-shot 才稳定。

> 冒烟局限：最小上下文（未加铁律 6/8/9、未给 few-shot、未注入码值），仅为隔离模型原始能力；
> 带上现有脚手架 smart-text 只会更好。Kimi 臂为文档结论非本轮重跑，严格同题对比以完整 A/B 报告为准。

### 9.2 完整模型 A/B 结论（2026-09-07，41 题，详见独立报告）

完整报告：`docs/Text2SQL_模型对比AB报告_2026-09-07.md`（受控 41 题，四模型同上下文）。要点：

| 模型 | 选对表 | 严格结果等价 | 逻辑正确(含仅round格式差异,估) |
|------|--------|-------------|--------------------------|
| smart-text | 41/41 (100%) | 8/41 (20%) | 13/41 (32%) |
| kimi-k2.6 | 36/41 (87%) | 8/41 (20%) | 18/41 (44%) |
| **kimi-k3** | 40/41 (97%) | **12/41 (29%)** | **19/41 (46%)** |
| kimi-k2.7-code | 38/41 (92%) | 9/41 (22%) | 18/41 (44%) |
| moonshot-v1-32k(线上,全链路基线) | 频繁错 | 1/41 (2.4%) | — |

- **P0 结论**：切 `kimi-k3` 是近零成本最大单点收益（严格 2.4%→~29%，选表→97%）；k3 > k2.6；本地可选 smart-text。
- **天花板 ~30~46%，模型换代必要不充分**：残留错**模型间高度一致**（`round()` 格式、码值分布口径、臆造过滤、
  明细 vs 汇总），是 P2/P3 靶点，换模型解决不了。
- **附带发现（评测口径）**：相当比例"失败"是 golden 约定问题（`round()`、分布 vs 计数），非模型错——
  **建议先修评测口径**（放宽数值格式、明确分布/计数），否则指标持续低估真实能力。

## 十一、风险

| 风险 | 缓解 |
|------|------|
| 多信号校验放大 token / 延迟 | 仅失败或低置信请求进入复核；轮次硬上限 3；端到端超时 ≤60s（承 REQ-002 D/F）；复用预算闸 |
| 值索引 DISTINCT 代价（大表） | 仅对码值/枚举类低基数列建索引；高基数列跳过；离线批量、错峰执行 |
| 富卡片自动生成质量 | 高频对象人工审核；同义词典业务方签字；低频兜底向量检索 |
| 语义层口径业务争议 | 17 指标口径须业务方签字后机器化（承 v1 风险项） |
| 嵌入/大模型微调数据污染 | 语料全部来自执行验证配对；抽样复核 |
| 相似表消歧误判 | 消歧步骤输出置信度，低置信触发歧义反问而非硬选 |

## 十二、与 v1 方案的关系（一句话）

方向承接 v1、数字承接 M1，主要修订**排序与核心机制**：
把押注从「一次生成 + 错误回喂」改为「**强接地检索（P1）+ 执行外多信号校验（P2）+ 高频模板化前移（P3）**」三线并进；
错误回喂降为 P2 的一个信号而非全部；微调仍垫底，且嵌入微调优先于大模型微调。
