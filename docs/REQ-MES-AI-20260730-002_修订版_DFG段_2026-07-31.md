## D. 预算与 §12 说明

### D1. 在线推理 token 预算

| 项 | 口径 | 数值 | 说明 |
|----|----|----|----|
| 首轮生成 | 每请求 | ~1.5K token | 与现状持平；schema linking 上线后按最小列子集重估，M2 复测回填 |
| 失败重试放大 | 平均放大系数 | **待基线报告回填** | 首日仅 4 例失败样本，不足以估算失败率；M1 基线报告出具后按实测失败率回填，回填前按**保守上限 2.0×** 预留 |
| 轮次上限 | 硬编码 | ≤3 轮 | 且触发提前终止条件即中断（见 F4） |

### D2. 评测流量预算（与业务日闸分账）

- 单轮全量评测：题库 N 题 × 3 次重复采样 × ~1.5K token ≈ **N × 4.5K token**；按筛后 N≈70 估算约 **32 万 token/轮**。
- 全周期评测轮次不止"基线 + 复测"两轮：开发调试期需反复回归，预估 **6~10 轮**，合计 **200~320 万 token**。
- **要求**：评测流量走独立标识（如 `channel=eval`）单独计量，**不挤占业务日闸**；超出评测配额时熔断评测而非熔断业务。

### D3. 可选增强（B2.4 候选采样）单列预算

- 3 候选 self-consistency 会使失败请求 token 放大至 **3× 以上**，与 D1 的 ≤2.0× 口径不兼容。
- **本单内默认关闭**（配置项 `retry.selfConsistency.enabled=false`）。如需启用，须单独提交预算说明并由 TL 二次签字，不在本单授权范围内。

### D4. 只读库负载

- 试执行 + golden SQL 执行均落在 MES 只读库，评测期间为**批量密集查询**，且部分生成 SQL 可能全表扫描。
- 约束：试执行强制加行数上限（`FETCH FIRST n ROWS ONLY` 或等效包装）；对预估代价过高的 SQL 先走 `EXPLAIN PLAN` 判定，超阈值直接判失败而非实际执行。
- 评测批量任务须限定在业务低峰窗口执行，并经 DBA 确认（见 H 段新增签字行）。

## F. 验收标准

### F1. 评测基线（对应 B1）

1. 评测可重复执行：同一题库、同一系统版本、连续两次运行，端到端准确率差值 ≤3 个百分点（否则判定评测本身不稳定，须先修评测再改系统）。
2. **评分口径明确落档**，至少包含：
   - **结果集等价定义**：值序列化后按行做集合比对，允许行序差异；列按位置对齐（不按别名）；数值统一定点比较（明确精度位数）；`NULL` 与空串不等价。
   - **空结果集处理**：golden SQL 返回空集的题目**单独标记并排除出主指标**，另计入"空集题目"子集报告。理由：当日失败案例 4（中文标签过滤）特征即为"执行成功但结果恒空"，若不排除会产生假阳性判对。
   - **数据漂移防护**：golden SQL 与生成 SQL 必须在**同一次评测运行中背靠背执行**，禁止缓存或复用历史 golden 结果。
   - **非确定性处理**：生成侧固定 `temperature=0`，每题重复 3 次取多数票；报告须给出每项指标的波动区间，不得只报单点值。
3. **指标分列定义**（不得混用）：
   - 生成率（返回了 SQL 的比例）
   - schema 校验通过率
   - **首轮执行成功率**（执行不报错）
   - **首轮结果正确率**（结果集等价判对）
   - 端到端准确率（含重试后的最终结果正确率）
4. **分层统计**：题库按 单表 / 多表 JOIN / 聚合 / 时间窗 / 码值过滤 至少五类打标，报告须给出**分层准确率**，不得只报总分。

### F2. 复测目标值（基线出具后确定）

- 本单**不预设固定提升点数**。M1 基线报告出具后，由 TL 在基线验收会上确认复测目标值并签字（见 H 段新增签字行）。
- 建议口径为**剩余错误率相对下降**而非绝对百分点：目标 **剩余错误率下降 ≥30%**（例：基线准确率 60% → 错误率 40% → 复测目标准确率 ≥72%）。
- 硬性下限（不可协商）：**首轮结果正确率不得低于基线**——防止 schema linking 改动在提升重试收益的同时损伤首轮质量。

### F3. 自纠错重试循环（对应 B2.1）

1. **重试路径专用触发用例集**（新增，必须）：当日四类失败案例在 v1.2 + 双保险状态下大概率首轮即通过，无法触发重试代码路径。故须构造专用用例：
   - 方式 A：以人工构造的错误 SQL + 对应 ORA 错误作为"上轮结果"直接驱动重试协议（单测层，覆盖消息拼装与收敛）；
   - 方式 B：临时关闭 Prompt 铁律 6/8/9 的对照配置下跑四类案例原题（集成层，覆盖端到端自纠错）。
   - **验收**：方式 A 全部用例通过；方式 B 下四类案例均在 ≤3 轮内无人工干预自纠错通过。
2. **四类实测失败案例作为首轮路径回归用例**保留，验收标准为"首轮即通过、不进入重试"。此项与上条分开计分，不得互相顶替。
3. 重试耗尽时返回 `generated=false` + 可读原因，不返回未通过校验的 SQL。

### F4. 收敛、延迟与用户体验（新增）

1. **提前终止条件**：连续两轮出现同一错误码 + 同一错误对象时立即终止重试，不烧满 3 轮。
2. **端到端超时上限**：含重试全链路超时须明确配置（建议 ≤60s），超时按失败返回。
3. **用户侧反馈**：进入重试时前端须给出可感知提示（如"正在校验并修正查询"），不得静默等待。
4. 报告须记录重试轮次分布（1/2/3 轮各占比）与平均端到端延迟，作为后续调优依据。

### F5. 归因可分离（新增）

复测须跑**三档消融**，否则单一数字无法区分收益来源：

| 档位 | `schemaLinking.enabled` | `retry.enabled` | 用途 |
|----|----|----|----|
| A（基线） | false | false | 当前 v1.2 + 双保险 |
| B | **true** | false | 隔离 schema linking 对首轮的影响 |
| C | true | **true** | 完整方案 |

对比报告须同时呈现 A/B/C 三档的 F1.3 全套指标。

### F6. 安全与合规防线

1. 每轮重试仍过 `SqlSafetyValidator` + `SqlSchemaValidator`，防线不降级。
2. **ORA 错误文本入模前经脱敏门过滤**：ORA 错误可能携带具体数据值（如 ORA-01722、约束冲突信息），回喂 LLM 构成本单**新增的"库→模型"数据通路**，须显式纳入脱敏门覆盖范围并留测试用例佐证。
3. **回喂列清单裁剪策略须落档**：全量 `all_tab_columns` 回喂与 B2.2"最小列子集防臆造"口径冲突，且大表数百列会撑爆上下文。须明确裁剪规则（如：仅回喂错误涉及表 + 与问题 schema linking 命中的列 + 错误列的近似匹配列，上限 n 列）。
4. 全程零硬编码；无任何写操作。

### F7. 测试

- 网关 pytest：重试收敛 / 重试耗尽 / 消息轮次拼装 / 提前终止 / 脱敏门覆盖 ORA 文本。
- Java JUnit：重试循环、终止条件、超时、预算熔断、双开关组合。
- 全部 `pytest` / `mvn test` 绿；新增用例明确覆盖 F3.1 方式 A 全部场景。
